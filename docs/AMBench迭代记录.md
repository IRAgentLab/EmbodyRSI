这个差别在五个任务上有清楚的对应：

1. **FrameAssembly：五天的数字，一句视频描述。** 09-19 至 09-24 早上，Claude 依据子判据、几何余量、EE oracle、质量参数、扰动开关、frame−ee 偏移，先后判定"余量被执行误差吃掉""浮空基座 x 漂移""负载稳态误差""近墙气动""框在夹爪里滑 18 cm"，全部错误；按这些判断做的一次性重规划、连续伺服都是 0/16。09-24 12:17 用户看完视频说"夹爪一直是紧的，但是 frame 会滑脱。很不合理"，Claude 随即查资产发现短柱无碰撞体，并在同一份录制里看到夹爪开度全程 0.002。这个数字早就在手里，但在"夹持滑动"的框架下没人去看它。
2. **TossBall：调试打印把人引向参数，探针把人引向几何。** 09-24 下午的逐步调试打印（穿透深度、接触力、指面高度）先后支持了"接触求解""摩擦不足""手指过轻"三个假设，改了刚度、迭代、摩擦、材质、质量，全部无效。转折来自两个最小对照：静止保持 4 s 不丢球（运动触发），单轴运动只有低头会丢（几何碰撞），再用资产测量找到前机臂。此前 09-19 的判据数字同样引出了"机体越线""判定区 z"两个错误假设。用户看视频的一句"一开始运动球就掉了，根本没抓住"推开了最底层的 reset bug。
3. **PushSlider：九个数字假设，一个视频现象。** 09-21 至 09-23，Claude 从动作块形状、净位移、静止比例、跟踪误差、推力饱和、指令抖动度、合爪时机、数据对比、归一化量程出发，提出的假设全部被证伪，对应的三次修改（低通、块融合、夹爪 oracle）两次有害一次无效。用户 09-22 看视频给出"可以夹住，拉的时候固定向上滑脱"，第一次把失败机制说准。之后的定位靠两个探针：专家在环回放 10/10（排除评测链），DP 30/30（排除数据），把问题收敛到"π₀.₅ 单相机"；最后是用户提出的机载视角解决了它。
4. **NDT：饱和数字给了反向的因果。** 跟踪误差 158 mm、饱和 91.7%、倾角 17° 让 Claude 认定"控制器跟不上"，两次减少锯齿的干预都失败。ACT 用同一份数据 30/30 这个对照，加上指令终点 z 9.26 vs 6.95 这个状态量，才把原因翻到"归一化让模型飞错了地方"。
5. **WipeWindow：连视频也会被误读。** 时序压缩（数字）有害，压深扫参（数字）不可判，Claude 用单集调试打印得出"海绵滑到位后稳住"，被用户的视频截图"海绵都掉了"推翻。但用户从同一视频得出的"夹紧一点就行"也错了。真正的根因来自代码审计（reset bug），接下来的"位置控制调不出力"来自带力打印的压深对照。

**反面证据也要记下：光看视频不够。** 有三个关键事实在画面里看不出来，只能靠状态量、逐步轨迹或资产检查：FrameAssembly 夹爪开度 0.002（空夹）、TossBall 的桶是实心的（渲染出来是一只正常的空桶）、球进桶瞬间被自动 reset 送回夹爪（在调试数据里表现为"弹开"）。视频类输入里也有错误：Claude 只看两帧就认错了桩和夹爪（I-14），用户从视频推出"夹紧一点"（I-53）。研究规划第 2 节对此的概括是"不看视频无法理解失败；光看视频也不够"。

**统计口径的局限**：判断的拆分和正确性由本文整理时判定；探针实验通常是在假设已经收窄之后才设计的，B 类的高正确率有选择效应；"用户直觉"一类里多数判断是方向性的，粒度比 Claude 的机制判断粗。

### 4.3 其他值得记的弯路

- **把约束当成事实**：WipeWindow 的录制时限（I-03）、config 里的 10k 步（I-01）、"A800 没有 RT Core 跑不了 Isaac"（第 6 节 #1）。三次都是把一个可改的配置当成不可动的约束。
- **在错误的前提上叠补丁**：WipeWindow 抬高 z 8.8 cm（I-52）是在补偿一个从没夹住的海绵；FrameAssembly 的一次性重规划和连续伺服（I-51）是在补偿一个没夹住的框。
- **用测试集挑配置**：5k/10k 取优（I-49）、跨版本组合最优 65.3 都用了评测集本身，Claude 在报告时标注了这一点，主指标同时给出只取 10k 终点的 54.7。
- **对着论文数字下结论**：WB-MPC 的 +26.7（I-12）、步数 40k（I-19）都是"论文里这样，所以我们这样也会涨"，在我们的实现里都不成立。
- **后台 agent 的无效消耗**：LingBot-VA 零样本 agent 335 次调用、约 50 万 token 无结果，Claude 接手后 5 分钟的配置对比就找到分辨率问题（I-23）；第一个 Cosmos agent 4 小时十几个作业一条 rollout 都没出。

几个读法：

- **评测数字的正确率最低**（17 个里对 1 个）。数字能告诉你"哪里坏了"，但在这一周里几乎没有一次能单独告诉你"为什么坏"。它更适合作为验证手段，而不是诊断手段。
- **代码阅读是双刃剑**。定位 reset bug、分辨率、扰动开关都靠读代码；但读代码也是错误假设最多的来源（14 个），常见错法是读了一半就下结论（只读 `build_openpi_example` 前半段）或者把配置当成事实（10k 步）。
